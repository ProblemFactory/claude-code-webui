## STEER-ALL PUT 25 MESSAGES IN THE TURN AND SHOWED ONE (2026-09-07, owner "我刚才在那个codex session里全给插入了，但是我只能看到我最后插入的一条消息")

In a long-running codex session the owner pressed **Steer all** on a 25-item queue. Every steer succeeded — the model demonstrably got all 25 — and the chat window showed exactly ONE new bubble: the message typed after the last resume.

**Where the messages came from.** The app-server's input queue belongs to the THREAD, not to the wrapper. The live buffer of the wrapper that came up at 07:06:43 UTC carries `queue_changed n=25` two seconds after boot, and every one of those 25 `clientUserMessageId`s is a webui msgId minted **~10 hours earlier**, by the wrapper this one replaced. So the queue was INHERITED across a Terminate+Resume while `queueMeta` — and every bubble the wrapper had ever written — started empty (all 25 `queue_op_result` frames carry `msg_id: ""`; the single message with a real msgId is the one typed at 07:38:03, the one bubble the owner saw).

**The hole.** A user bubble comes from the record the wrapper writes as the text passes THROUGH it (`handleInput`). For a submission it never typed, the only live notice is the app-server's own carrier — `item/completed {item:{type:'userMessage', id, clientId, content}}` (0.153.4 `UserMessageThreadItem`; the rollout persists the same thing as `item_completed` / `UserMessage` / `client_id`, 28 of them at 07:38:44-45, each immediately after its `response_item`, with **no `user_message` event anywhere**: the queued path's carrier does not exist on the steered path). That kind fell off the end of `_handleItemCompletedInner` with **no branch and no breadcrumb**, so twelve-plus messages entered the turn in silence. Reproduced against the shipped wrapper in-suite: 12 steers OK, 1 bubble.

**A second defect the same session data exposed:** every message the user TYPES renders twice after a reload. One message is written by BOTH producers — us (as it is sent, carrying `webui_msg_id`) and codex (when the app-server commits it, carrying its own `msg_…` id and nothing of ours) — and `recordFingerprint` keys the first by ID and the second by CONTENT, so `mergeCodexRecords` dedupped neither. Measured through the REAL reader over the owner's real 66MB rollout + live buffer: 3/3 typed messages doubled.

**FIX, at three layers:**
1. **Wrapper (`data/bin/codex-chat-wrapper.js`).** `item/completed` routes `userMessage`: `recordInboundUserMessage(clientId, userInputToContent(content))` writes the bubble for any submission ENTERING the turn whose id we have not already recorded. A landed `turn/steer` records it AT ONCE, in queue order (the commit twins arrived 42s later on the owner's session — a message that went in must be visible when it went in; a REFUSED steer records nothing, that message is still queued). `recordedUserCids` remembers every id whose bubble already exists (chat-input msgId, the generated `queued-…` id, the peer cid), and an item with **no** clientId is ours by construction — only `turn/start` carries none. The record's `webui_queue_id` marker is out-of-band on both readers; the queue ROW advertises the same clientUserMessageId as its `msgId` so the strip row and the bubble's `Steered` chip join.
2. **Normalizer (`src/codex-message-manager.js`).** `webui_queue_id` is a SECOND-CLASS identity: stamped into `webuiMsgId` (`_stampUserIdentity`) so the chip joins, but it does not suppress peer detection (most inherited items were agent-to-agent messages and must keep their labelled card) and `recordKey` strips it like `webui_peer`, so both copies of one message mint the same id.
3. **Store (`src/codex-session-store.js`).** The inherited bubble's marker is stripped from `recordFingerprint` (both copies are written inside the turn that commits the message, so their turn-scoped content keys agree), and the ID-KEYED twin gets a **claim**: an id-carrying copy of ours claims its content key and the next codex-side copy of that content consumes it and is dropped — n copies in, n bubbles out. Ours survives, so the chip join and the live message id are preserved.

**INVARIANTS.** (a) **Every kind an upstream stream can emit is either routed or NAMED** — the wrapper is an allowlist too, and it had no `else`; a kind that is neither gets logged once verbatim and counted in `meta.unhandledItems` (`noteUnhandledItem` / `NO_RENDER_COMPLETED_ITEMS`), because the absence of that breadcrumb is exactly how `userMessage` stayed lost. (b) **State that outlives the process is not ours to assume**: the app-server's queue survives a wrapper restart, so "we have a bubble for everything in it" was only ever true for the wrapper that filled it — anything entering the turn under an id we do not know needs a record. (c) **A message that enters the turn must be visible when it enters**, not when the server gets round to committing it. (d) **The twin rule is FORWARD ONLY**: a claim covers copies that come after it (ours is always written first), because letting a late claim swallow an EARLIER codex record would delete an old message from history the moment its text was typed again after the buffer had rotated — a millisecond tie renders twice instead, since a duplicate is a nuisance and a deletion is data loss. (e) **A falsy id is not an identity** — a `webui_msg_id: ''` copy keys on content like codex's, or it is a stranger to its own twin.

**Gates.** scripts/test-codex-p2-wrapper.mjs ⑥ (the REAL wrapper against a stub that hands it an inherited queue: steer-all → 12 bubbles in order, the late commit twins add nothing, a DRAINED item gets its bubble from the twin alone, our own message is never re-recorded, the unhandled-kind breadcrumb — plus a PRE-FIX control run verbatim from `git show master:data/bin/codex-chat-wrapper.js`, which reproduces "12 steers, 1 bubble"). scripts/test-queue-steer.mjs ⑨ (the redacted rollout-shape fixture scripts/fixtures/codex-steer-all-rollout.jsonl → 12 bubbles from the rollout alone and 12 from the 24-record rebuild, with negative controls at 24 and 2; the drained cross-turn twin; two identical texts staying two; the forward-only guard; the peer-card guards; and a headless-chrome leg that renders the real normalizer's messages with the REAL renderer and counts twelve bubbles, ten of them chipped `Steered`).
## AUTO-RESUME FIRED 130 TIMES INTO A WALL (2026-09-07, owner's frozen journal + screenshot; owner decision ut-1c6c15a2db items ①④ — items ② ledger backfill and ③ projection-driven re-reads stay OPEN)

**Symptom.** One conversation was auto-continued **130 times** between 23:32 and 04:03 (a second one 32 times, up to two per SECOND). Every continue was a billed turn the CLI answered with "You've hit your session limit · resets 6am". About 150 of the conversation's last 150 messages (2295–2445 of 2445) were the same three junk artefacts repeating: the CLI's error line, VibeSpace's injected "自动续跑" prompt, and a "账号池已切换到 PandyMax，已自动继续这个任务。" card.

**What the evidence said.** Every cycle in the journal is byte-identical apart from timestamps:

```
[auto-resume] <id>: armed for <now+45s> (switched to a usable account)
[pool] per-session switch <pool>/<id>: <observed> (observed; linked <link>) → <link> (re-point, same target)
[auto-resume] <id>: 账号池已切换到 <link> — continued immediately
```

740 of those `(re-point, same target)` lines — the pool "switching" a session to the member it was already linked to. The final arm at 04:03:48, once a real reading finally landed, names every member dead **including the one the engine had spent four and a half hours calling usable**, and ends `— session observed on Fish Max while linked to B-Stack Max`.

**Root cause (two independent defects; both reproduced before either was touched, scripts/test-auto-resume-loop.mjs).**

① **Attribution.** B-2c9b (plan B) made the OTel-observed org override the link for BLOCKING decisions, on the premise that "a hot-switched CLI keeps its old token, so the observation names what it is burning". The owner's post-mortem corrected the premise: `organization.id` on an `api_request` is the identity the CLI cached in its **config dir at SPAWN**, not the token that authorized the request — the credential file itself IS re-read, which is exactly what the re-point's mtime bump exists for. So every rejection was filed against the org the session had STARTED on, the linked member — whose credentials the process actually reads — never received a wall verdict and stayed "healthy" in the cache forever, `quotaVerdictFor` answered "usable via \<link>" on every cycle, the per-session pass decided FROM the (dead) observed member and therefore "switched" to the link it was already on, and the hot-switch path called `fireNow()`.

② **No memory.** Neither fire path remembered that the previous continue onto that exact identity had been rejected seconds earlier, and `fireNow` skipped the pre-fire gate (`beforeFire`) that the timed path runs — so the one component that re-probes and re-verdicts before spending was bypassed by the path that fired 130 times.

**The fix.**

- **A rejection is a fact about the credential SLOT.** `wallSlotFor(session)` resolves the session's own per-session symlink (or the pool's default link) and VALIDATES it — a real member of this pool (`validateBillingSlot`; named failures `no-slot` / `slot-not-a-member` / `slot-unreadable` — `poolMembers()` already filters by loggedIn, so a separate credentials leg would be an unsatisfiable guard, and the suite pins that every named reason is reachable). Its `slotOk` verdict travels **on the wall signal**, because it is only true at the moment the rejection ARRIVES: by the time the turn ends the pool has usually re-pointed the link off the account that just refused us (measured — the first version validated at turn end and reported "not this session's credential slot" about the very account that had rejected it).
- **One function no longer answers two questions.** `sessionBillingMember` (link + slot validation) answers every BLOCKING question: the demotion target, the verdict order and `viaId`, the per-session switch's `currentId`, both quota-probe targets, `_wallScope`, and the loop breaker's fire identity. `sessionReadingMember` (observed over link — the old body verbatim) answers only `resolveUsageKey`: the live odometer, probe-session matching and derived cache keys. B-b3cd's odometer-flap defence is untouched, because a utilization **number** really does describe whatever token produced it, while a **rejection** describes the credentials that were read.
- **The verification ladder gains a top rung.** A wall on the session's own validated slot is ground truth by itself — we know what the symlink points at, which is strictly better evidence than a telemetry attribute. Every other account still needs the 2.368.34 corroboration (≥2 walled turns in 120s, or it IS the observed org), and the journal names which rung authorised it: `(1 walls / credential slot)`, `(1 walls / observed-org)`, `(2 walls / 2-walls)`.
- **A per-SESSION memory.** `noteSessionWall(sid, member)` records "this member rejected THIS conversation" for 10 minutes — written even when the demotion is HELD, because "it rejected me" is true either way — and is unioned with the breaker's `recentFireFailures`. `quotaVerdictFor` cannot answer `usable` through such a member, and `decidePoolSwitch({exclude})` cannot pick one. `exclude` is a NAMED pure input reported as `all-rejected`, never a silently empty candidate list; `pessimism` was the wrong tool because "it just said no to this conversation" is not a percentage, and docking it would let a big enough gap re-select the member on the very next tick.
- **The loop breaker** (auto-resume.js). A fire the session answers with another limit rejection is a FAILED fire; the record `{identityKey, at, count}` is per session and is PERSISTED with the armed waits, because a deploy must not hand the loop a fresh budget. Four named refusals: `fire-pending` (never two continues in flight), `same-identity` (10min quarantine), `backoff` (immediate fires 0 / 60s / 5min), `hourly-cap` (3 immediate fires per session per hour, after which only the TIMED path — the one anchored to a real reset — may fire). Both paths became ONE `attemptFire`, so the immediate path runs the same `beforeFire` gate; `_arFiring` is raised BEFORE the gate is called, because the real gate runs `maybePoolAutoSwitch` → `fireNow` and everything before its first `await` is synchronous re-entry (measured 1992 levels deep with the flag one line late). `onWalledTurn` reports the failure FIRST, before anything re-arms or re-switches — that ordering is the off-switch — and `noteRecovered` clears the breaker BEFORE its armed-record early return, since a fire has already deleted the armed record.
- **One honest line.** When the breaker trips the session is told once per window: "账号池已切换到 X，但它同样被用量上限拒绝… 将在 T 重置后自动继续" or "…且暂时没有可用的成员 — 可以添加成员、把这个会话切到别的账号，或等待配额重置". The success line ("已切换到 X，已自动继续") is likewise once per distinct target per session per window; the incident wrote it ~150 times. A refused TIMED fire stays journal-only — it self-heals inside 10 minutes, so saying it would be noise.

**Invariants.**
- A fire answered by a limit rejection is a FAILED fire, and that fact must survive a restart.
- "Where do I fire" and "who rejected me" must be the SAME fact, or the breaker quarantines an account that never rejected anything.
- A judgement about "which account is this session on" is only valid at the instant the evidence arrives — by the end of the turn our own pool switch has rewritten it. Carry the verdict on the signal.
- A telemetry attribute is not a credential. Values belong to the token that produced them; a REJECTION belongs to the credential slot that was read. We OWN the symlink — that is the stronger evidence.
- Every "no way out" outcome must speak (one operator line, one user line), but an outcome that self-heals in minutes must stay quiet.
- The negative control for a two-defect incident is a MATRIX, not a snapshot: re-create each pre-fix behaviour through a public seam and show that removing either one alone stops the failure (both off ⇒ ≥10 unbounded fires here).

**Round 2 (adversarial verifier; four defects, all reproduced through the real engine before anything was touched).**

- **① The "one honest line" was one line for four different facts (medium).** `logRefusal` computed the named check `chk` and then dropped it: `breakerNotice` hard-coded the exhaustion narrative for EVERY reason. Reproduced at module level and through the real engine + real pool: the first continue goes out onto Account A, the pool re-points onto healthy Account B, the second attempt is refused `fire-pending`, and the conversation is told *"账号池已切换到 Account B，但它同样被用量上限拒绝，且暂时没有可用的成员。已停止反复重试…"* — **B had never been fired at, B and the rest of the pool were healthy, and the session was still ARMED** (it continues ~15 s later on the tick). Worse, that card SPENT the once-per-window budget, so the genuine "nothing can serve you" line was then suppressed for the rest of the hour (measured: the real same-identity refusal that followed said nothing at all). The harsh variant is the one users hit, because it triggers when `resetsAt <= now + 5min` and the near-arm is always `now+45s`. Fix: the text is a PURE function of the refusal reason (`refusalNoticeFor`), and each class has its OWN budget. `same-identity` may say "it refused us too"; the additional clause "and there is nowhere else to go" requires a SECOND fact — the pool's own no-target verdict, handed over by `noteNoPoolTarget` from the `all-rejected`/`no-members`/`stuck` branch of the per-session pass — never an inference from a refusal reason. `hourly-cap` says exactly what it knows (N tries this window, immediate retries paused). `backoff` and `fire-pending` are JOURNAL-ONLY and spend nothing: they are sub-minute pacers on a promise that is still being kept, and no-silent-failures is about a BROKEN promise. A card that says "stopped retrying" seconds before retrying is a lie the user has to un-learn.
- **② The fire was recorded against the account we LEFT (medium).** `attemptFire` resolved the identity BEFORE the pre-fire gate — and the gate is `beforeAutoResumeFire`, which runs `maybePoolAutoSwitch` and can re-point the credential link. Reproduced with a real pool {DeadOne (5h at 1), HealthyOne (5%)}: the tick's gate moved the link, the continue was delivered while linked to HealthyOne, and `_fires.last.key` said DeadOne — so a rejection would quarantine the account we had already left, leave the REAL rejector fireable, journal the wrong name, and dedup the card under the wrong key. This is precisely the invariant round 1 wrote above `identityFor()` ("the fire onto X failed" and "X rejected this session" must name the same X), broken in the one case that comment warns about. Fix: `deliver()` re-resolves the identity after the gate, re-runs `canFire` on it (a gate that moves us onto an identity we already burned this window ABORTS instead of spending), and keys `noteFired`/`announce`/the journal to where the continue actually landed.
- **③ The card claimed the quota had reset when the pool had swapped accounts (low).** The timed path announced "用量上限已重置" unconditionally — and after round 1 that is the DOMINANT recovery path (see ④), so the common case now told the user something false. Fix: the wording comes from what actually unblocked us — `kind === 'now'` (always a pool switch), a near-arm reason (`switched to a usable account` / `account usable again`), or the identity having MOVED during the gate; only with none of the three is "the limit reset" the reason. A drift guard pins the two arm-reason strings against the engine that writes them.
- **④ The suite certified an ordering production does not take (low).** §2's leg "a hot per-session switch still continues the armed session immediately" INJECTED the wall signal, which skips the early `maybePoolAutoSwitch` that BOTH real producers run. Measured on one world, changing only the producer: **injected `noteWallSignal` ⇒ 1 immediate continue; real `recordRateLimitEvent` ⇒ 0; real `markLimitBanner` ⇒ 0.** The link is re-pointed to the healthy member BEFORE `onWalledTurn` arms the session, so the `finally` pass has nothing left to switch and `fireNow` is never reached; the session is armed at +45 s and continued by the TICK — **45 s arm + 15 s grace on a 30 s tick ⇒ ~60–90 s, not "immediately"**. §2 now drives both real producers and pins that latency, keeps the injected leg only as a labelled artificial control, and adds the case the immediate path actually exists for (c1206711: a switch that lands LATER onto an already-armed session — driven through `maybePoolAutoSwitchForPool`, the engine's own seam, with the wall-clock eval gate and dwell belt wound back instead of slept through). §4b's "the cache is untouched" had the same shape — it only held because the signal was injected; a real rejection writes its own reading (`source: rate-limit-event`, utilization 1) through `captureRateLimitEvent` before the ladder runs. It now asserts the LADDER's output (no `wall`-sourced write, the named hold/`not-a-member` verdict) and a companion leg drives the real producer to show both writers.

**Round-2 invariants.**
- A refusal may only claim what its OWN reason knows. Four named reasons are not one message with four spellings, and the clause "there is nowhere else to go" belongs to whoever computes it (the pool), not to whoever noticed a retry was too soon.
- A notice budget is per CLAIM, not per module: one shared stamp lets a frequency notice eat the only line that carries an actionable fact.
- No-silent-failures covers a BROKEN promise. A pacing refusal on a session that is still armed and does continue is journal-only — narrating it is noise that the next event contradicts.
- Any state a GATE can change must be re-read after the gate. Resolving an identity, then running a gate whose whole job is to re-point that identity, then recording the pre-gate value, mis-keys everything downstream — and the re-read must re-run the admission check, not just relabel.
- The text that explains a billed turn must name the fact that caused it. "The limit reset" and "the pool switched" are different events; deriving both from the armed record (plus "did the gate move us") keeps one source for the card and the journal line.
- **A test that INJECTS a signal has chosen an ordering.** When two producers exist, the suite must drive the real ones and state the measured latency; the injected leg survives only as a labelled control, next to the measurement that shows why it differs.

## THE EFFORT A TURN RAN AT — OUR SYNTHESIZED TWIN OUTLIVED THE TRUTH (2.369.62, owner "我刚才把那个van的对话调成了 ultra, 但我看它回复怎么都 metadata 显示的是 xhigh?")

**Symptom.** A conversation the owner had set to `ultra` reported `xhigh` in the message-metadata popup on every single reply, for the whole session.

**What the evidence said.** codex's own rollout carries `turn_context.effort = ultra` on every turn since 2026-09-06T20:33 (21/21, plus its own `thread_settings_applied` records), the usage ledger says `ultra`, and `data/session-meta` said `ultra`. But the LIVE buffer of that session — 1137 records — contained exactly ONE `turn_context`: the wrapper's synthesized copy at `07:06:44.566Z`, effort `xhigh`. codex's own copy of the SAME turn says `ultra` at `07:06:46.484Z`.

**Root cause (three faults stacked).** ① The wrapper synthesizes the `turn_context` every reader takes a turn's effort from, at `turn/started` — and 0.153.4's `TurnStartedNotification` is `{threadId, turn:{id,status,…}}` with **no effort and no model**, so the value comes from our own bookkeeping. It printed the mutable `effort` var = the SPAWN ENV, which on this resume was the instance default `codex.defaultEffort = xhigh`. ② The turn was started by the APP-SERVER (an auto-continue on resume: `goal_cleared`, `turn/started`, then the `thread/resume` reply — all inside 07:06:44.565-.566Z), so we never sent `turn/start` and that value had never reached codex at all; the reply carrying `reasoningEffort:'ultra'` landed 1.9ms LATER and only assigned `meta.effort`, leaving the emitted record and the `effort` var alone (the adoption at updateMetaFromThread is gated on `!effort`). ③ That single record was the only `turn_context` in the buffer — the app-server steered and drained everything inside that one turn — so `CodexMessageManager._status.effort` stayed `xhigh` and every `token_count` baked `xhigh` onto every message. A fourth fault kept it from ever healing: `mergeCodexRecords` fingerprints a turn_context on its turn id and kept the FIRST copy, and ours is always the earlier of the twins — so codex's authoritative copy was suppressed on every rebuild, forever.

**Fix.** Three named facts replace one var in the wrapper (`effort` = commanded-next, `threadEffort` = the app-server's own word, `turnEffort` = what the ACTIVE turn runs at); a turn WE start uses what we put on `turn/start` (which also re-points the thread, per TurnStartParams' own doc, reverted on refusal), a turn the app-server starts uses the THREAD's; `noteTurnEffort()` RESTATES the same turn id when the resume reply lands late; `wrapper_meta` carries the `{effort, effortNext}` pair (mid-turn attach, no rollout re-read); `set-effort` now also sends `thread/settings/update {effort}` so a turn the app-server starts on its own runs at the value the UI is claiming; the merge folds a repeated turn_context into the first copy but takes the better copy's VALUES (codex's own always wins); and the normalizer splits `_status.effort` (this turn) from `_status.effortNext` (pending) with one writer that also pushes a live `meta/effort` op.

**Invariants.** ① A record that states what a turn IS RUNNING AT may only carry a value that reached the agent — the pending/commanded value belongs in its own field, and a pick made mid-turn never relabels messages the running turn already produced. ② When we synthesize a twin of a record the agent also writes, the agent's copy MUST win the fold — ours is structurally the earlier one, so first-wins silently makes our guess permanent. ③ A knob the UI presents as "applies from now on" must be told to the party that will act on it (`turn/start` alone is not enough when the app-server starts turns by itself). ④ A liveness/state check must read the process's own immediate statement, not a debounced sidecar — the 200ms `scheduleMeta` lag is enough to queue a message into the turn you just stopped (caught by this fix's own test bench). ⑤ 'ultra' is a MODE, not a level: state both facts from the catalog or state only the mode; never hardcode the level.

**Known residue (owner gate, NOT changed here — filed as backlog B-6b6d).** `codex.defaultEffort` is documented as applying to "new **or resumed** Codex sessions", and the client sends it as `data.effort` at `src/lib/session-lifecycle.js` (`sessionEffort = effort !== undefined ? effort : defaults.effort`), which suppresses ws-create's B-21e4 EFFORT-CONTINUITY fallback (`lastCodexTurnEffort`) — whose whole purpose is that a resume "can never flip a conversation that was running at high/ultra". **Precise scope** (r2 review corrected the first wording, which read as if every resume were affected): the card's gear popover writes a per-session override and `resumeSession` forwards it, so the bite is limited to resume paths that supply nothing — the **chat resume bar**, **resume-all**, and any card with no saved override — where `savedCfg.effort` is `undefined` and the instance default takes its place. The **MODEL twin is the identical line** (`sessionModel` / `lastCodexTurnModel`, ws-create.js:394) and is unchanged for the same reason. Flipping the priority ("only apply the instance default when there is no `resumeId`") is a product-default decision ⇒ owner gate, and it must move effort and model together (STANDING SWEEP). What this release does instead is make it VISIBLE and stop it corrupting the record: the session's saved effort is now honest (the wrapper's own value reaches `session._effort` + session-meta, so a `/effort` typed into the chat no longer leaves a stale value behind for the next resume), and the status-bar tooltip says which value the turn in flight is really running at. Leg ⑪ pins both twins plus the mechanism itself (the adapter really does leave `CODEX_WEBUI_EFFORT` empty when nothing is supplied, and really does fill it when the default is), so a half-fix fails red.

**Round 2 (adversarial verifier; four defects, all reproduced before fixing).**
- **① The version marker named someone else's release (major).** The branch stamped `2.369.61` into 36 places across 17 files while master had ALREADY SHIPPED `2.369.61` (Alt+Enter = steer) — 16 seconds before this branch's own commit. Same class as the 2.369.58 r2 renumber off `2.369.54`. Renumbered to **2.369.62** in one pass. No ref ⇒ explicit SKIP, never a silent pass.

**INVARIANTS.** (a) A verification window sized for the moment of corruption expires the moment anything is appended after it — a decision that ADOPTS unverified bytes must pay for evidence over the whole artifact, and record that it did so, so the cost is paid once. (a2) That record must be a marker THIS code writes (a schema version), never a field the buggy code also wrote: gating a heal on "the old code left this blank" misses every slot the old code filled in on its way past the bug — and a fix's own release window is where those slots come from. (a3) Name the harm the fix removes, then prove the fix removes THAT: a change that is separately correct ("record the adoption") can be shipped with a false causal claim attached ("…so growth syncs"), and a test that quietly relaxes the condition under test (dropping `maxBytes` on the growth poll) will agree with it. (a4) Advice inside an error message is a claim about the system — if the branch that emits it can only be reached where the advice cannot work, it is a false claim, not a courtesy. (a5) A guard nobody can delete-and-fail is not a guard: every legality clause owes a leg that goes RED when that clause alone is removed — and when the clause exists in twin form on two rungs, it owes one on EACH, or the copies drift the moment one is edited. (a6) A fast path added under an existing one must leave the slow path REACHABLE: replacing the only road with an optimisation turns every failure mode of the optimisation into a failure of the whole feature, and on the LAST rung there is nothing below to catch it — fall back where the slow path is still possible, and hard-fail only where it provably is not. (a7) A meta writer overwrites what it just LEARNED, never what it inherited: durable provenance and a fresh object literal are contradictory designs, and the field that gets erased is always the one that cannot be re-earned. (a8) A read-then-write against a size measured before the read is a lost update waiting for a second caller: serialize the RESOURCE (the cache slot), and make the write itself refuse the offset it was computed from once that offset is no longer the end of the file — a positional write at a re-checked offset is idempotent where a blind append is a duplicated region. Corollary for the repro: a duplication whose records are IDENTICAL is byte-identical to the correct file, so a fixture built from repeated records will pass the negative control while the bug is fully present. (a9) **A refusal is only a refusal on the rung that can be reached.** A guard thrown inside a try whose catch degrades to another implementation is not a guard — it is a slower path to the same corruption, because the fallback re-derives its inputs from the very state the guard refused to trust. Classify the throw: a TRANSPORT failure may degrade, a verdict about the shared RESOURCE must be terminal on every rung and must travel as a CODE the fallback tests, never as a message nobody reads. (a10) **A guard that only sees the race window has to be paired with one that reads the evidence the race left behind.** An in-window check (re-read the offset through the fd you are about to write with) expires the moment the poll ends: next time round, the foreign bytes are simply part of the file and every in-window question answers "fine". The durable form asks a record the code wrote itself — grow only what we stamped — which also means every writer must stamp what the file ACTUALLY holds, or the invariant starts reading our own fetches as foreign. Corollary: when a fix's negative control needs three separate neuterings to reproduce the original bug, that is not redundancy to trim — it is three independent legs, and the suite should be able to remove each one alone and go red. (a11) **A rule written for a corruption will also condemn every innocent shape that wears the same signature — find them before shipping it, because the rule's own remedy may not exist for them.** "The file holds more than we stamped" is foreign bytes AND our own short stamp, and the branch where a whole refetch is impossible is exactly where the innocent one dies permanently. Two consequences: gate the strict rule on a marker THIS code writes so it is absolute only where it is provably right (a10's corollary — a writer that stamps the real length cannot over-stamp), and when local evidence cannot separate the two shapes, ASK THE SOURCE OF TRUTH for the disputed bytes instead of loosening the rule (a bounded read that compares them is positive evidence; a splice scan is only absence of one kind of evidence). The heal that follows must be bounded to the case with no other remedy, paid once, durable the moment it is proven, and its refusals must be remembered in MEMORY — a refusal stamped on disk freezes the corruption in. (a12) A degrade-path log obeys the "say what you swallowed" law AND the "do not say it 500 times" one: rate-limit per host and carry the suppressed count forward — a suppressed fault is not a forgotten fault. (b) Any rewrite a validator performs on a declared path must be a rewrite the consumer performs too; where they differ, refuse rather than emit the wider form (a normalization that widens a grant is a silent privilege escalation). (c) The rule "count only what the USER did" has to enumerate everything that is not the user — one exception (our nudge) is a hint that there are others (a peer message). (d) An in-flight request belongs to the turn that started it: when that turn is cancelled, record the cancellation and DISCARD the answer — never let a round trip that outlived its turn start a billed one.

- CodeMirror active-line highlight hid the selection on the first/last selected line: `highlightActiveLine` (from `basicSetup`) decorates the line under the selection HEAD even during a range selection, and that background paints on `.cm-line` ABOVE the selection layer (`z-index:-1`), so the opaque light-theme active-line (`#f1f5f9`) covered the selection rect on that one line. Fix: tag the editor `.cm-has-selection` when any range is non-empty + a theme rule `&.cm-has-selection .cm-activeLine{background:transparent}` (outranks light + oneDark `.cm-activeLine`). **Focus gotcha:** first attempt toggled the class directly on `view.dom` via a ViewPlugin — but CodeMirror rebuilds `view.dom.className` from scratch on every focus change (`updateAttrs` → `"cm-editor" + (cm-focused) + themeClasses`), wiping the class, so the highlight reappeared once the editor lost focus. Correct way: contribute the class through the **`EditorView.editorAttributes` facet** (a function value) — `attrsFromFacet` re-evaluates it on every update (incl. selection + focus, `updateAttrs` runs at the end of each view update) and `combineAttrs` CONCATENATES its class into the className CM builds, so it survives blur. Both editors share `activeLineSelectionPatch` (exported from code-editor.js). Lesson: never mutate `view.dom.classList` on a CodeMirror editor — it's clobbered on focus/theme changes; use the editorAttributes facet.
