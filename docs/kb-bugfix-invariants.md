## A MEMO KEY THAT NAMED NEITHER THE PRICES NOR THE LEDGER (2.369.43, review batch — the 2.369.36 interval memo's two holes)
The inc-mtox23xw fix memoized `costBetweenMulti` on `ids|from|to|events-at-or-before-to`. Both remaining holes were reproduced before fixing. ① PRICING: the key names the LEDGER but not the PRICE TABLE, and `_cost` reads `this._pricing` live — so after a pricing edit (a tier rate or a per-account discount, POST /api/usage-stats/pricing or a config import through persistence.js) every already-memoized historical interval kept returning pre-edit dollars forever, poisoning the estimator's learned rates and every anchor's `costSince` while the Usage window (which does not go through the memo) showed the new numbers. Repro: a 10× opus tier edit and a 50% account discount each left the total frozen at $3.50 against a truth of $35.00 / $17.50. FIX: `UsageHistory.pricingToken()` = a sha1 of {tiers, accounts}, recomputed only when `_pricing` is REPLACED (the same object-identity check `_tier` uses), appended to the key; a ledger object that cannot version its prices is NOT memoized at all. ② EVICTION: `learnRates` walks one identity's anchor pairs in the SAME order on every recompute — a cyclic reference string, the one access pattern where FIFO (and LRU) go off a CLIFF instead of degrading. Measured on the shipped code: a 20000-key working set hits 100%, 21000 hits **0.0%** — a 5% overshoot destroys 100% of the memo and the per-pair ledger walk of inc-mtox23xw comes straight back. Real anchor files are append-only forever (production: 5124 qualifying pairs over 28 days across 8 identities, ~180 new/day, biggest identity 1126), so the 20000 cap is reached in months, not never. FIX: a RANDOM victim (O(1) via a parallel key array) — the same input now holds 53% at 1.3× the cap. Also: the memo moved from a module global to a WeakMap per UsageHistory, so two ledgers can never read each other's costs through a key that names neither. **INVARIANTS: a memo over computed values keys on every INPUT of the computation, not just the data it walks (a rate table, a discount, a rounding rule are inputs); if an input cannot be versioned, do not memoize; an eviction policy is chosen against the ACCESS PATTERN — recency policies are worst-case for repeated full scans, and "cap exceeded" must degrade, not cliff; a cache keyed by values that name no instance belongs to the instance (WeakMap), never to the module.** Pins: scripts/test-usage-ledger-perf.mjs (21) — price-edit/discount/clear parity vs brute force, hit-path parity, cross-ledger isolation, and a hit-rate floor at 1.3× cap (both negative-controlled: dropping the token reddens 4, true FIFO reddens the hit-rate assert at exactly 0.0%).

## CODEX .ZST / DISCOVERY / REMOTE-FETCH BATCH (2.369.x, review findings — four ways a codex thread went missing or came back wrong)

**① A RATIO GUESS DECIDED WHETHER A THREAD EXISTED.** `readHeadText` (discovery-facts) read a bounded COMPRESSED prefix and one-shot decompressed it under `maxOutputLength: max(plainBytes*4, 1MiB)`; anything compressing better than ~4× threw EZSTBIG, the `catch { return ''; }` turned that into an EMPTY head, `extractCodexThreadMeta` produced `threadId: ''`, and the thread VANISHED from /api/sessions — then the empty meta was cached by mtime, so for a stopped thread it stayed gone until a restart. Measured on the dev box: compressing the 40 real `~/.codex` rollouts at the DEFAULT zstd level, 7 reproduced it (ratios 4.0–6.0, e.g. plain 1,115,325 → comp 195,087). Fix: `zstdDecompressHead` BISECTS over compressed prefix sizes under a fixed output cap (a truncated prefix decompresses to the plain text it covers — verified on this runtime) until ≥ plainBytes of plain text exist; an unreadable head now THROWS a coded error (`EZSTUNSUPPORTED`/`EZSTHEAD`; zero plain bytes out of non-empty compressed input is a failure, not emptiness) so the existing `extractFailed` rule refuses to cache it, and `_noteExtractFailure` logs the reason verbatim once per file per 10 min. **Invariants: a bounded reader must be bounded by CONSTRUCTION (bisect/stream), never by a guessed compression ratio; "unreadable" and "empty" are different answers and only the second may be cached; a degrade path that hides a thread must say so in the log.**

**② A CACHE GUARD MEASURED THE WRONG CLOCK.** The codex rollout walk's per-directory listing cache (`codex-session-store._listDirCached`) skipped the readdir when the dir mtime was unchanged AND `now - mtime > 2s` — the coarse-timestamp guard evaluated at LOOKUP time. Settledness is a property of the CAPTURE: a listing taken while the mtime tick was still open can miss a sibling created in the same second, and that sibling never bumps the mtime again, so once the clock passed mtime+2s the stale listing was trusted forever (the poll is 5s — the window is always over by the next lookup) and the second rollout never appeared in the session list. Fix: record `settled` at fill time; an unsettled capture is re-read on the next lookup until it is taken settled (the readdir-per-poll win is untouched for settled captures). **Invariant: a freshness/settle predicate is evaluated and STORED when the data is captured — evaluating it at read time answers a question about the reader, not about the data.**

**③ "PLAIN WINS" WAS A COMMENT, NOT A RULE.** `interpretDiscoveryLines` de-duplicated a thread's `.jsonl` and `.jsonl.zst` twins by keeping the FIRST entry, commented "plain wins — first in mtime order". Both producers sort newest-first (hosts.js `sort -rn`, agentd.js `b.mtimeMs - a.mtimeMs`) and compression happens AFTER the last write, so the compressed twin was always first — and the ssh scanner can only read a compressed head where the host has `zstd(1)`, so the remote card silently lost the cwd/name its plain twin's HC/NC lines carried. Fix: group by thread id, prefer the plain twin's facts EXPLICITLY, MERGE what each twin has (either fills a gap), mtime = the newer of the pair, CO on either twin marks the one thread running. **Invariant: when two files describe one entity, the preference is expressed in the predicate, never inherited from an upstream sort; a dedup that drops facts must merge them instead.**

**④ ONE CACHE SLOT, MANY REMOTE FILES.** `hosts._fetchRemoteByFind` keys `data/remote-jsonl/<host>/codex/<tid>.jsonl` by conversation id, but codex's `remoteFind` predicate matches the plain rollout OR its `.zst` twin, so `find … | head -1` could resolve a DIFFERENT file across polls (the host compresses a finished rollout). The meta recorded only {size,mtime,fetchedAt,slab}, so the append-only delta path concatenated the new file's bytes onto the other file's cached prefix and stamped the result complete — and a stopped thread never changes again, so the corrupt transcript was served forever. Fix: the meta records `remotePath` + `compressed`; a changed path invalidates the slot (full refetch, no cache-valid short-circuit); a compressed remote — or an already-compressed cache file, detected by magic bytes so pre-fix metas are covered — is never delta-appended; the locate pipeline is `find … | sort | head -1` so the pick is deterministic and prefers the plain twin. **Invariants: an incremental/delta sync must verify the SOURCE identity, not just its size and mtime; a cache slot shared by several possible sources records which source filled it; a locate that may match several files sorts before it picks.** **④b THE FIX DID NOT HEAL WHAT WAS ALREADY BROKEN (same batch, review follow-up).** Provenance protects the slots the FIXED code writes — but every slot in the field already carried a meta without `remotePath`, and the first cut read that as “same file” (`!meta.remotePath || …` is vacuously TRUE), so a cache the old delta path had ALREADY spliced (plain prefix + the twin’s bytes, stamped complete) kept passing the size/mtime short-circuit — forever, since a stopped thread never changes again and nothing else invalidates the slot. A migration whose trigger is “the remote moved” never runs for the exact population it was written for. Fix: a meta WITHOUT provenance is NOT valid — refetch whole ONCE and rewrite it (and it may not delta either) — plus the cache FILE now testifies about itself: its head magic must agree with the resolved remote (zstd bytes under a plain remote, or the reverse, = the other twin’s bytes in the slot) and a plain cache whose last 4KB hold a NUL byte or a zstd frame header is spliced (an append always lands its foreign bytes at the TAIL). The ONE exception to “heal by whole refetch” is a remote already past `maxBytes` — a whole refetch is impossible there (the delta path is how such a slot grew), and failing “too large” on a transcript that worked yesterday is worse than trusting the byte check, so a verified cache adopts the provenance we just resolved. **Invariants: when a fix adds a field the correctness check depends on, records written BEFORE it are not “unknown, assume fine” — they are the corrupted population, and the missing field must read as INVALID; a self-heal must not be gated on the broken input changing; and a cache’s own bytes are stronger evidence than its metadata about those bytes.** Pins: scripts/test-codex-zst.mjs ①b/③/④b/⑥/⑥b (real-shaped >4× fixture at default level, twin order both ways, utimesSync same-tick repro, stub device switching remote files under one slot, and a pre-written hybrid cache + old-shape meta that heals with the remote standing still — each with the pre-fix predicate asserted as the negative control).
## ACP WRAPPER: STOP DIDN'T STOP, DENY RAN THE TOOL, AN EXIT-0 AGENT DIED SILENTLY (review batch over data/bin/acp-wrapper.js, after 2.369.31)

Four defects in the generic ACP v1 client, all reproduced against the REAL wrapper over pipes (scripts/dev/mock-acp-agent.mjs), all four now pinned in scripts/test-acp-harness.mjs (86).

**① Stop lost a race with the prompt-context fetch.** `runPrompt` claims the turn SYNCHRONOUSLY (so a second message queues) and only then awaits `fetchContextPrefix()` — a real HTTP round trip to /api/agent/prompt-context. A Stop landing inside that await saw `activePrompt`, flipped `cancelled` and sent `session/cancel`; the await then returned and dispatched the prompt anyway, so the wire read `initialize → session/new → session/cancel → session/prompt` and the agent — which had no turn to cancel — ran the whole turn the user had just stopped (and, like the mock, an agent may LATCH that cancel and kill the NEXT turn instead). Fix: `runPrompt` holds its own turn handle (`mine`) and re-checks `mine.cancelled` after the await, before dispatch: a cancelled prompt emits `prompt_end` with stopReason `cancelled` (shared `endPrompt` path, so streaming/meta/queue-drain stay identical) and is never sent. The interrupt verb also only emits `session/cancel` for a turn it actually dispatched (`mine.dispatched`) — an undeliverable cancel is worse than no cancel.

**② The interrupt verb kept the queue.** ACP has no queue verb, so the wrapper holds queued prompts locally; the old handler cleared them only in the `else if` branch that runs when NOTHING is active. Stop during a turn therefore cancelled it and the cancelled turn's own `drainPromptQueue()` immediately dispatched the queued prompt — the agent kept working, with a second permission request, right after Stop. Fix: interrupt ALWAYS splices the queue and says how many it dropped (`queue-cleared` notice). A queued PEER message was already reported delivered (`peer_result` ok/queued), so dropping it silently would lose a promised message: each dropped peer entry re-emits `peer_result {ok:false,text,fromName}` (the queue entry carries `opts.peerText/peerFrom` for exactly this) and the acp-events consumer re-stashes it on the delivery ladder.

**③ A Deny selected an ALLOW option.** `resolvePermission`'s last-resort fallback was `msg.approved ? options[0] : options[options.length - 1]` — positional, not kind-checked. An ACP agent is free to offer only `[allow_once, allow_always]` (the option list is the agent's), and then the LAST option is `allow_always`: a rejection executed the tool AND stood the permission down for the rest of the session (reproduced: `{approved:false}` → selected `always` → tool_call_update completed). Fix: FAIL CLOSED — a rejection with no reject-kind option answers `{outcome:'cancelled'}` (ACP's own no-answer outcome; the tool does not run) and emits a `deny-cancelled` notice saying what the Deny became, because cancelled may end the turn rather than just refuse the tool; approvals keep the positional fallback. Today's desktop client only sends `approved:false` without an optionId from the option-less permission card, so this was a latent contract hole rather than a live UI path — the wrapper's stdin verbs are a documented contract and a Deny must never be answerable with an allow.

**④ An agent exiting 0 before `initialize` produced ZERO records.** The child-exit handler gated its boot-failure notice on `code !== 0`, and `finalizeExit()` calls `process.exit()` synchronously — so `boot()`'s own catch (the `boot-failed` notice) never runs from that path either. An agent that quits 0 before answering initialize (a CLI printing usage because the acp subcommand changed, an unauthenticated agent giving up quietly) left an empty journal and an empty buffer file: a blank chat window that never said why, the ACP twin of the "dead session = blank shell" class. Fix: the notice fires whenever the agent exits before the session is ready, whatever the code (text names `exit code 0` / `signal X`), and the journal IS the history so the buffer file carries it across a restart.

**INVARIANTS: ① a flag captured before an await is re-checked after EVERY await before the side effect it guards (a synchronously-claimed turn plus an async prefix is a race by construction) — and never send a control message for work the peer does not know about; ② "Stop" is total: local queues are part of the stopped state, and anything dropped that was already reported delivered goes back to the delivery ladder, never quietly discarded; ③ a permission fallback fails CLOSED — a rejection may never resolve to an allow-kind option, and a rejection expressed differently than the user asked must SAY so; ④ exit code 0 is not success when the protocol handshake never completed — report the failure on the record channel the window rebuilds from, not only on a non-zero exit.**

- CodeMirror active-line highlight hid the selection on the first/last selected line: `highlightActiveLine` (from `basicSetup`) decorates the line under the selection HEAD even during a range selection, and that background paints on `.cm-line` ABOVE the selection layer (`z-index:-1`), so the opaque light-theme active-line (`#f1f5f9`) covered the selection rect on that one line. Fix: tag the editor `.cm-has-selection` when any range is non-empty + a theme rule `&.cm-has-selection .cm-activeLine{background:transparent}` (outranks light + oneDark `.cm-activeLine`). **Focus gotcha:** first attempt toggled the class directly on `view.dom` via a ViewPlugin — but CodeMirror rebuilds `view.dom.className` from scratch on every focus change (`updateAttrs` → `"cm-editor" + (cm-focused) + themeClasses`), wiping the class, so the highlight reappeared once the editor lost focus. Correct way: contribute the class through the **`EditorView.editorAttributes` facet** (a function value) — `attrsFromFacet` re-evaluates it on every update (incl. selection + focus, `updateAttrs` runs at the end of each view update) and `combineAttrs` CONCATENATES its class into the className CM builds, so it survives blur. Both editors share `activeLineSelectionPatch` (exported from code-editor.js). Lesson: never mutate `view.dom.classList` on a CodeMirror editor — it's clobbered on focus/theme changes; use the editorAttributes facet.
