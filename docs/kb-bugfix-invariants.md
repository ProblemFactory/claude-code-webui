## THE EFFORT A TURN RAN AT — OUR SYNTHESIZED TWIN OUTLIVED THE TRUTH (2.369.62, owner "我刚才把那个van的对话调成了 ultra, 但我看它回复怎么都 metadata 显示的是 xhigh?")

**Symptom.** A conversation the owner had set to `ultra` reported `xhigh` in the message-metadata popup on every single reply, for the whole session.

**What the evidence said.** codex's own rollout carries `turn_context.effort = ultra` on every turn since 2026-09-06T20:33 (21/21, plus its own `thread_settings_applied` records), the usage ledger says `ultra`, and `data/session-meta` said `ultra`. But the LIVE buffer of that session — 1137 records — contained exactly ONE `turn_context`: the wrapper's synthesized copy at `07:06:44.566Z`, effort `xhigh`. codex's own copy of the SAME turn says `ultra` at `07:06:46.484Z`.

**Root cause (three faults stacked).** ① The wrapper synthesizes the `turn_context` every reader takes a turn's effort from, at `turn/started` — and 0.153.4's `TurnStartedNotification` is `{threadId, turn:{id,status,…}}` with **no effort and no model**, so the value comes from our own bookkeeping. It printed the mutable `effort` var = the SPAWN ENV, which on this resume was the instance default `codex.defaultEffort = xhigh`. ② The turn was started by the APP-SERVER (an auto-continue on resume: `goal_cleared`, `turn/started`, then the `thread/resume` reply — all inside 07:06:44.565-.566Z), so we never sent `turn/start` and that value had never reached codex at all; the reply carrying `reasoningEffort:'ultra'` landed 1.9ms LATER and only assigned `meta.effort`, leaving the emitted record and the `effort` var alone (the adoption at updateMetaFromThread is gated on `!effort`). ③ That single record was the only `turn_context` in the buffer — the app-server steered and drained everything inside that one turn — so `CodexMessageManager._status.effort` stayed `xhigh` and every `token_count` baked `xhigh` onto every message. A fourth fault kept it from ever healing: `mergeCodexRecords` fingerprints a turn_context on its turn id and kept the FIRST copy, and ours is always the earlier of the twins — so codex's authoritative copy was suppressed on every rebuild, forever.

**Fix.** Three named facts replace one var in the wrapper (`effort` = commanded-next, `threadEffort` = the app-server's own word, `turnEffort` = what the ACTIVE turn runs at); a turn WE start uses what we put on `turn/start` (which also re-points the thread, per TurnStartParams' own doc, reverted on refusal), a turn the app-server starts uses the THREAD's; `noteTurnEffort()` RESTATES the same turn id when the resume reply lands late; `wrapper_meta` carries the `{effort, effortNext}` pair (mid-turn attach, no rollout re-read); `set-effort` now also sends `thread/settings/update {effort}` so a turn the app-server starts on its own runs at the value the UI is claiming; the merge folds a repeated turn_context into the first copy but takes the better copy's VALUES (codex's own always wins); and the normalizer splits `_status.effort` (this turn) from `_status.effortNext` (pending) with one writer that also pushes a live `meta/effort` op.

**Invariants.** ① A record that states what a turn IS RUNNING AT may only carry a value that reached the agent — the pending/commanded value belongs in its own field, and a pick made mid-turn never relabels messages the running turn already produced. ② When we synthesize a twin of a record the agent also writes, the agent's copy MUST win the fold — ours is structurally the earlier one, so first-wins silently makes our guess permanent. ③ A knob the UI presents as "applies from now on" must be told to the party that will act on it (`turn/start` alone is not enough when the app-server starts turns by itself). ④ A liveness/state check must read the process's own immediate statement, not a debounced sidecar — the 200ms `scheduleMeta` lag is enough to queue a message into the turn you just stopped (caught by this fix's own test bench). ⑤ 'ultra' is a MODE, not a level: state both facts from the catalog or state only the mode; never hardcode the level.

**Known residue (owner gate, NOT changed here — filed as backlog B-6b6d).** `codex.defaultEffort` is documented as applying to "new **or resumed** Codex sessions", and the client sends it as `data.effort` at `src/lib/session-lifecycle.js` (`sessionEffort = effort !== undefined ? effort : defaults.effort`), which suppresses ws-create's B-21e4 EFFORT-CONTINUITY fallback (`lastCodexTurnEffort`) — whose whole purpose is that a resume "can never flip a conversation that was running at high/ultra". **Precise scope** (r2 review corrected the first wording, which read as if every resume were affected): the card's gear popover writes a per-session override and `resumeSession` forwards it, so the bite is limited to resume paths that supply nothing — the **chat resume bar**, **resume-all**, and any card with no saved override — where `savedCfg.effort` is `undefined` and the instance default takes its place. The **MODEL twin is the identical line** (`sessionModel` / `lastCodexTurnModel`, ws-create.js:394) and is unchanged for the same reason. Flipping the priority ("only apply the instance default when there is no `resumeId`") is a product-default decision ⇒ owner gate, and it must move effort and model together (STANDING SWEEP). What this release does instead is make it VISIBLE and stop it corrupting the record: the session's saved effort is now honest (the wrapper's own value reaches `session._effort` + session-meta, so a `/effort` typed into the chat no longer leaves a stale value behind for the next resume), and the status-bar tooltip says which value the turn in flight is really running at. Leg ⑪ pins both twins plus the mechanism itself (the adapter really does leave `CODEX_WEBUI_EFFORT` empty when nothing is supplied, and really does fill it when the default is), so a half-fix fails red.

**Round 2 (adversarial verifier; four defects, all reproduced before fixing).**
- **① The version marker named someone else's release (major).** The branch stamped `2.369.61` into 36 places across 17 files while master had ALREADY SHIPPED `2.369.61` (Alt+Enter = steer) — 16 seconds before this branch's own commit. Same class as the 2.369.58 r2 renumber off `2.369.54`. Renumbered to **2.369.62** in one pass. The belt that existed (test-harness-honesty's CHANGELOG rule) could not see it: a branch that is not rebased has no CHANGELOG entry for EITHER number, so the check passes vacuously. **The number is claimed on the INTEGRATION BRANCH, so the check has to ask git** — leg ⑩ scans `origin/master`'s release-commit subjects AND its CHANGELOG headings for the marker and fails unless the claimant IS this change, with the old number `2.369.61` as a standing negative control (it must still read as claimed-by-someone-else, or the check is blind). No ref ⇒ explicit SKIP, never a silent pass.
- **② `effortNext: null` is a statement, not a gap (minor).** The new session-meta writer read `payload.effortNext || payload.effort` — re-conflating the two facts the release exists to separate. Picking "Auto (model default)" makes the wrapper clear the thread's effort and publish `{effort:'<the last turn ran at>', effortNext:null}`; the fallback then wrote the last turn's LEVEL into `session._effort`, session-meta, the attach payload's `chatStatus.effortNext`, the chip after a restart and the next resume spawn — overwriting the `null` ws-handler had just written on the same click. Now `effortNext` is the only field read, and only when present (`undefined` = an old wrapper says nothing ⇒ master's behaviour, the 2.361.1/2.364.1 skew rule).
- **③ A record in codex's spelling that codex refused (minor).** `set-effort` emitted `thread_settings_applied` — codex's OWN rollout shape — unconditionally, including after `thread/settings/update` was rejected, and unmarked. Our payload carries 5 `thread_settings` keys where codex's real one carries 9 (`model_provider_id`, `approvals_reviewer`, `collaboration_mode`, `permission_profile`…), so the two can never share a fingerprint and a rebuilt history kept both forever. Now: recorded only when the RPC was ACCEPTED (a refusal leaves the per-turn `turn/start` fallback, and the pending pick still reaches every client through `wrapper_meta.effortNext` — a statement about US, which a refusal leaves true), and both wrapper-authored copies carry `wrapper: true` like the synthesized `turn_context`. `mergeCodexRecords` folds the twin the same way (codex's copy wins), keyed on the stated VALUES and scoped to ADJACENCY — high → ultra → high is a real sequence, and folding the third into the first would leave a rebuilt status reporting `ultra`.
- **④ The disclosed resume gap needed an owner, not a paragraph (minor).** Filed as B-6b6d with the MODEL twin; scope corrected above.

**Round-2 invariants.** ⑥ A version marker is a CROSS-REFERENCE: it must resolve on the branch it will be integrated into, and the only source that knows is git — a CHANGELOG check on an un-rebased branch is vacuous by construction. ⑦ `null` from a producer that always sends the field is a VALUE ("nothing pending"); only `undefined` is absence. Never `a || b` across two fields that mean different things — that is the exact conflation the incident is about, re-introduced one layer down. ⑧ Never write a record in another party's spelling for something that party did not do; if you must synthesize one, MARK it, and let the real author's copy win the fold.

Gate: scripts/test-codex-effort-meta.mjs (108) — the race reproduced against a stub app-server with the REAL wrapper, plus per-defect regression legs with negative controls (master's own record shapes; a REFUSING app-server; `effortNext:null` vs an old wrapper's absent field; adjacent-vs-sequential settings twins; the squatted version number).
## B-7638 — THE SEVEN REVIEW RESIDUALS (the 2026-09-06 review-fixes-r2 verify; every one reproduced before it was fixed)

Three fixes shipped in that batch each left something behind that the verify pass named and the repro confirmed. They are unrelated in code and identical in shape: **a rule was written for the state the incident happened to be in, and the state it drifts into afterwards was never asked about.**

**① The over-cap adoption trusted a 4 KB window (src/hosts.js).** The remote-transcript cache heals a pre-provenance slot by refetching it whole, with ONE exception: a remote already past `maxBytes` cannot be refetched at all, so a byte-verified cache adopts the provenance instead of failing "too large". "Byte-verified" read the last 4 KB — sound at the moment of a splice, because an append lands its foreign bytes at the TAIL. But the pre-fix delta path kept appending AFTER it spliced, so on any long-lived slot the marker is buried under later appends and a tail read calls the hybrid verified — forever, because a stopped thread never changes again. The whole-file scan (1 MiB chunks, 3-byte carry so a zstd magic split across a boundary is still seen) is the evidence such a slot owes. **Round 2 corrected WHICH slots owe it.** The first cut gated the deep scan on "the meta carries no `remotePath`" — but that is exactly the provenance the *shipped* tail-only adoption used to stamp: it adopted a buried hybrid and the delta path then wrote `remotePath` onto that very slot, so `sameRemote` is TRUE for the corruption the scan exists to find, and every slot that passed through the ⑥ window would have been served on a tail check forever. The gate is now a meta SCHEMA MARKER (`v: 2`) written by every meta writer in `_fetchRemoteByFind`: any meta from before this fix pays ONE whole-file scan the first time its bytes are trusted, and is re-stamped so the cost is paid once per slot, never per poll. A refused slot is left unstamped.

**① b The cap error's remediation could not work (src/hosts.js).** The same batch appended "delete it to re-sync" to the "too large" error when the cache did not verify. The suffix is reachable ONLY when the remote is past the cap — where a whole refetch is impossible by construction — so following the advice destroyed the last local copy and failed identically (verified: delete cache → same error; delete cache AND meta → same error). It now states the true situation: no prefix to grow from, the remote is past the *N* MB cap, and deleting the cache would not help. Advice in an error message is a claim about the system; it needs the same evidence as any other claim.

**② The ssh rung could not grow an over-cap slot (src/hosts.js).** Both early-return branches handed the verified cache back and left the meta unstamped, so the whole-file scan repeated on every poll; `stampVerified` (remotePath + compressed + `adopted` + the schema marker) on both rungs ends that — **and that is all the stamp does**. The round-2 verify caught the first cut claiming more: the *harm* here was that the legacy ssh rung hard-failed "remote transcript too large" on the very next byte of growth, and stamping provenance changes nothing on that path (the short-circuit needs `meta.size === size`, so any growth falls straight into the cap throw, with no fallback to the verified cache — a >64 MB transcript that opened yesterday was an error today). The real fault was a TWIN GAP: the slab rung has grown an over-cap slot by an append-only delta since 2.187.0 and the ssh rung only ever whole-`cat`ted, so the same conversation behaved differently depending on which transport happened to serve it. The ssh rung now carries the same delta (`tail -c +N`, 1-based on GNU and BSD), under the same legality test (same remote file, uncompressed on both sides, cached prefix no longer than the remote) and the same never-stamp-bytes-we-did-not-get rule — with one refinement the last rung needs: a read that OVERTAKES the stat (a live transcript grew mid-poll) keeps the extra bytes, because an append-only file's extra tail bytes are genuinely its next bytes, and stamps what the cache actually holds; only a SHORT read throws.

**② b ROUND 3 — the three residuals of the round-2 delta itself (src/hosts.js).** The verify that passed round 2 named them, and each was reproduced before it was fixed.
  **(i) The compression-legality clause had no negative control on either rung.** `canDelta`/`canDeltaSsh` both carry `!isZstPath(remotePath) && !cacheIsCompressed()`, and DELETING it left test-codex-zst ALL PASS — the suite only ever exercised the twin-SWITCH (plain ⇄ .zst), never a growth with BOTH sides compressed. That case is the innocent-looking one and the worst: a host re-compresses a finished rollout, so the remote keeps its path, the cache holds .zst bytes that verify (for a compressed slot the magic IS the evidence), and the cached archive is shorter than the remote — every other delta precondition holds. The "delta" would weld a foreign frame tail onto the old frames; `zstdDecompressFrames` then stops at the earlier frames and the slot serves the OLD transcript, with the growth silently gone. Both rungs now carry a both-compressed growth leg (⑥d) whose asserts go red when the clause is deleted from EITHER copy — the two legality tests are twins, and a guard only one copy carries is the drift this batch keeps paying for.
  **(ii) The delta REPLACED the last rung's whole `cat`.** Round 2 added `tail -c +N` to the ssh rung as an `if/else` against the whole-`cat` branch, so a `tail` that FAILS — the remote truncated/rotated between the stat and the read, or a host whose `tail` has no `-c +N` — now hard-fails a fetch the pre-r2 code completed, and this is the LAST rung: nothing under it to fall through to. A delta failure now falls back to the whole `cat` when `size <= maxBytes` (logging the failure VERBATIM, per the degrade-path rule), and the hard error is kept ONLY over the cap — where a whole re-pull is impossible by construction and the delta really was the only road, so the fallback can never become a cap bypass. The over-cap short-read hard failure from round 2 is unchanged.
  **(iii) The meta writers rebuilt provenance instead of carrying it.** Both rungs stamped a FRESH object at the end of a fetch, so the very next delta erased `adopted` (the marker meaning "these bytes were VERIFIED, never fetched") and the `slab` lane marker — the exact opposite of the durability ① claims, and it landed on the one slot class that can never re-earn it (an over-cap slot cannot be refetched to prove itself again). One shared `nextMeta(fields, {whole})` now spreads the prior meta on BOTH rungs; only a WHOLE refetch clears those two markers, because they describe bytes that are no longer in the slot.

**② c ROUND 4 — TWO POLLS, ONE SLOT, ONE OFFSET (src/hosts.js).** Both rungs are now read-then-append against a size measured BEFORE the remote read, and nothing serialized the SLOT. Two overlapping fetches of the same conversation — the 5s session poll and a user opening the window, two clients, goal-sync and an attach — each read `fs.statSync(cachePath).size`, each asked the host for `[localSize, size)`, and each appended it: the cache grew a DUPLICATED region. That much self-heals (a doubled file no longer matches its own meta ⇒ whole refetch), which is why three review passes walked past it; the permanent damage is one poll later. Once the remote grows past the doubled size the legality test holds again, the next tail is appended at the doubled offset, and the file's size now EQUALS the remote's — so the stamp says COMPLETE and the short-circuit serves it forever, with a region duplicated and the region behind it MISSING. Nothing catches it downstream either: duplicated JSON records carry neither a NUL byte nor a zstd magic, so the byte checks of ① are silent, and a stopped conversation never changes again. Two independent legs, because the failure has two independent sources. **(i) The slot is single-flighted**: `_fetchRemoteByFind` is now a thin wrapper over the core (`_fetchRemoteByFindOnce`) holding an in-flight promise per cache path — a second caller AWAITS the first's verdict instead of racing it (one remote read, one append; every caller resolves its cap from the same harness descriptor, so a coalesced caller cannot lose a cap it needed, and the next poll re-decides with its own). **(ii) The append refuses a stale offset**: `_appendDeltaAt(cachePath, offset, buf)` opens `r+`, re-reads the size THROUGH the fd it is about to write with, and writes POSITIONALLY at `offset` — at a matching offset the write is idempotent, at a mismatching one it does not happen at all. `false` means "the slot moved": under the cap that is a whole refetch on both rungs (the ssh rung reuses the round-3 fallback), over the cap — where a whole re-pull is impossible by construction — it is a loud failure that leaves the slot exactly as it was found. Pins: test-codex-zst ⑥f, with pre-fix repros for both legs (the doubling, then the poll that seals it and the short-circuit that then serves it forever) and mutation-tested one leg at a time: deleting the single-flight reddens the two coalescing asserts on both rungs, deleting the offset check reddens the four moved-slot asserts.

**② d ROUND 5 — THE REFUSAL THAT DEGRADED (src/hosts.js).** Round 4's moved-slot refusal was correct and unreachable on the rung that needed it most. The over-cap `throw` sits INSIDE the data-plane `try`, and that catch means "this TRANSPORT did not work, try the other one" — so on a dial host (or any host with the data plane on) with a reachable ssh fallback the refusal landed in `catch (e2) { /* legacy fallback below */ }`, silently, and the ssh rung then measured `fs.statSync(cachePath).size` on the MOVED file, computed a fresh tail offset from it and appended: the remote's bytes for the moved region were never fetched, the file's size nevertheless EQUALS the remote's, the meta stamps COMPLETE, and a stopped conversation serves the hole forever. Reproduced verbatim (dial transport, foreign 203-byte append during `fsReadRange`, remote past the cap): no error, no log line, `meta.size == remote size`, remote bytes [P, P+203) missing — and the next poll short-circuited on it. Three legs, each mutation-tested alone. **(i) The verdict is typed.** `slotMovedError` carries `code:'ESLOTMOVED'` and the catch re-throws it (`_isTerminalFetchError`): a statement about the CACHE is true on every rung; only TRANSPORT failures may degrade. **(ii) What a rung learned outlives it.** `observed.moved` (`_slotMovedEarlier`) denies the ssh rung a delta even when the slab rung reached the fallback for an unrelated reason — it can observe the movement, refetch whole UNDER the cap, and then have that whole read die on the wire. **(iii) The durable half.** One poll later the movement is invisible to `_appendDeltaAt`: the foreign bytes are simply in the file, the offset it re-reads MATCHES them, and the append lands right behind them — so the fix would only have delayed the corruption by one poll. `_prefixIsOurs(localSize, meta)` asks the meta instead of the clock: a delta may extend only bytes this cache's own writers stamped (the file may not hold MORE than `meta.size`). A SHORTER file stays growable on purpose — a positional append only ever writes at the end, so a short file is still a genuine prefix (a crash between the append and the meta write, a truncation), and refusing it would strand every over-cap slot that ever crashed mid-write. Over the cap every one of these is a loud failure that leaves cache AND meta byte-identical, and the cap error names WHICH fault it is ("could not be verified" vs "holds N bytes where the last fetch stamped M"). Two consequences fell out: the whole `cat` now stamps `buf.length` instead of the stat it was promised (a live transcript hands back more bytes than the probe said — the tail branch of the same rung has always stamped the real length, and an under-claiming meta would make (iii) read our own fetch as foreign bytes), and the data-plane catch now LOGS every fault it swallows VERBATIM — it logged nothing at all, which is how a degrade path hides a lost binding for three days (2.340.2).

**③ A transcript shorter than the magic could never be verified (src/hosts.js).** `head.length < 4 ⇒ refetch` meant an empty or one-record transcript was fully re-pulled on EVERY poll, forever. A cache under 4 bytes cannot BE a zstd frame and cannot hide a splice: it verifies (still subject to "a .jsonl cache starts with a record"), while a sub-magic cache under a COMPRESSED remote is still refused.

**④ A home-dir dot glob widened to every user (src/plugin-manifest.js).** 2.369.44 taught the validator that node reads a declared fs path only up to the first `*` and grants by STRING PREFIX; 2.369.43 taught it to collapse `.` segments the way node does. At `~/.*` the two rules collide: node keeps `.*` as an ordinary segment (the grant is the prefix `<home>/.` — dotfiles), but collapsing the dot HERE emitted `<home>*` — the whole home directory plus every sibling path starting with those characters (`/home/u*` reaches `/home/u2/…`). The manifest said one thing and node was handed another, invisibly. A `.` segment immediately before `*` is now refused, naming the prefix it would have produced.

**⑤–⑦ The ACP bookkeeping nudge is OURS, not the user's (data/bin/acp-wrapper.js).** Three consequences of one confusion:
  ⑤ The 'queue-cleared' notice ("send it again") subtracted dropped NUDGE entries but not dropped PEER ones — and a peer message is not the user's to re-send either: it goes back to the delivery ladder on `peer_result ok:false` and arrives again on its own, so the advice was both wrong and impossible to follow. Nudges AND peers are subtracted now; the log line keeps the true total.
  ⑥ The nudge queued with a visible `queued_input`, painting a "Queued" chip on a bubble that does not exist. It queues with `silentQueue` (as peer messages already did) and stays visible in `queue_changed` as kind 'system', so the strip is still honest about what is waiting.
  ⑦ **A Stop landing inside the `/api/agent/stop-check` round trip still billed a turn.** The nudge is fetched by `endPrompt` and dispatched when the answer lands — by then the interrupt has finished and `activePrompt` is null, so the fetch resolved straight into `runPrompt` and started a fresh turn the user had just asked to stop; the only trace was a reminder appearing out of nowhere. The interrupt now bumps `stopEpoch` and aborts the request in flight, and an answer whose epoch is gone is discarded with a logged reason. The latch is never set on that path, so the NEXT completed turn nudges normally.

**INVARIANTS.** (a) A verification window sized for the moment of corruption expires the moment anything is appended after it — a decision that ADOPTS unverified bytes must pay for evidence over the whole artifact, and record that it did so, so the cost is paid once. (a2) That record must be a marker THIS code writes (a schema version), never a field the buggy code also wrote: gating a heal on "the old code left this blank" misses every slot the old code filled in on its way past the bug — and a fix's own release window is where those slots come from. (a3) Name the harm the fix removes, then prove the fix removes THAT: a change that is separately correct ("record the adoption") can be shipped with a false causal claim attached ("…so growth syncs"), and a test that quietly relaxes the condition under test (dropping `maxBytes` on the growth poll) will agree with it. (a4) Advice inside an error message is a claim about the system — if the branch that emits it can only be reached where the advice cannot work, it is a false claim, not a courtesy. (a5) A guard nobody can delete-and-fail is not a guard: every legality clause owes a leg that goes RED when that clause alone is removed — and when the clause exists in twin form on two rungs, it owes one on EACH, or the copies drift the moment one is edited. (a6) A fast path added under an existing one must leave the slow path REACHABLE: replacing the only road with an optimisation turns every failure mode of the optimisation into a failure of the whole feature, and on the LAST rung there is nothing below to catch it — fall back where the slow path is still possible, and hard-fail only where it provably is not. (a7) A meta writer overwrites what it just LEARNED, never what it inherited: durable provenance and a fresh object literal are contradictory designs, and the field that gets erased is always the one that cannot be re-earned. (a8) A read-then-write against a size measured before the read is a lost update waiting for a second caller: serialize the RESOURCE (the cache slot), and make the write itself refuse the offset it was computed from once that offset is no longer the end of the file — a positional write at a re-checked offset is idempotent where a blind append is a duplicated region. Corollary for the repro: a duplication whose records are IDENTICAL is byte-identical to the correct file, so a fixture built from repeated records will pass the negative control while the bug is fully present. (a9) **A refusal is only a refusal on the rung that can be reached.** A guard thrown inside a try whose catch degrades to another implementation is not a guard — it is a slower path to the same corruption, because the fallback re-derives its inputs from the very state the guard refused to trust. Classify the throw: a TRANSPORT failure may degrade, a verdict about the shared RESOURCE must be terminal on every rung and must travel as a CODE the fallback tests, never as a message nobody reads. (a10) **A guard that only sees the race window has to be paired with one that reads the evidence the race left behind.** An in-window check (re-read the offset through the fd you are about to write with) expires the moment the poll ends: next time round, the foreign bytes are simply part of the file and every in-window question answers "fine". The durable form asks a record the code wrote itself — grow only what we stamped — which also means every writer must stamp what the file ACTUALLY holds, or the invariant starts reading our own fetches as foreign. Corollary: when a fix's negative control needs three separate neuterings to reproduce the original bug, that is not redundancy to trim — it is three independent legs, and the suite should be able to remove each one alone and go red. (b) Any rewrite a validator performs on a declared path must be a rewrite the consumer performs too; where they differ, refuse rather than emit the wider form (a normalization that widens a grant is a silent privilege escalation). (c) The rule "count only what the USER did" has to enumerate everything that is not the user — one exception (our nudge) is a hint that there are others (a peer message). (d) An in-flight request belongs to the turn that started it: when that turn is cancelled, record the cancellation and DISCARD the answer — never let a round trip that outlived its turn start a billed one.

## A MEMO KEY THAT NAMED NEITHER THE PRICES NOR THE LEDGER (2.369.43, review batch — the 2.369.36 interval memo's two holes)
The inc-mtox23xw fix memoized `costBetweenMulti` on `ids|from|to|events-at-or-before-to`. Both remaining holes were reproduced before fixing. ① PRICING: the key names the LEDGER but not the PRICE TABLE, and `_cost` reads `this._pricing` live — so after a pricing edit (a tier rate or a per-account discount, POST /api/usage-stats/pricing or a config import through persistence.js) every already-memoized historical interval kept returning pre-edit dollars forever, poisoning the estimator's learned rates and every anchor's `costSince` while the Usage window (which does not go through the memo) showed the new numbers. Repro: a 10× opus tier edit and a 50% account discount each left the total frozen at $3.50 against a truth of $35.00 / $17.50. FIX: `UsageHistory.pricingToken()` = a sha1 of {tiers, accounts}, recomputed only when `_pricing` is REPLACED (the same object-identity check `_tier` uses), appended to the key; a ledger object that cannot version its prices is NOT memoized at all. ② EVICTION: `learnRates` walks one identity's anchor pairs in the SAME order on every recompute — a cyclic reference string, the one access pattern where FIFO (and LRU) go off a CLIFF instead of degrading. Also: the memo moved from a module global to a WeakMap per UsageHistory, so two ledgers can never read each other's costs through a key that names neither. **INVARIANTS: a memo over computed values keys on every INPUT of the computation, not just the data it walks (a rate table, a discount, a rounding rule are inputs); if an input cannot be versioned, do not memoize; an eviction policy is chosen against the ACCESS PATTERN — recency policies are worst-case for repeated full scans, and "cap exceeded" must degrade, not cliff; a cache keyed by values that name no instance belongs to the instance (WeakMap), never to the module.** Pins: scripts/test-usage-ledger-perf.mjs (21) — price-edit/discount/clear parity vs brute force, hit-path parity, cross-ledger isolation, and a hit-rate floor at 1.3× cap (both negative-controlled: dropping the token reddens 4, true FIFO reddens the hit-rate assert at exactly 0.0%).

## CODEX .ZST / DISCOVERY / REMOTE-FETCH BATCH (2.369.x, review findings — four ways a codex thread went missing or came back wrong)

**① A RATIO GUESS DECIDED WHETHER A THREAD EXISTED.** `readHeadText` (discovery-facts) read a bounded COMPRESSED prefix and one-shot decompressed it under `maxOutputLength: max(plainBytes*4, 1MiB)`; anything compressing better than ~4× threw EZSTBIG, the `catch { return ''; }` turned that into an EMPTY head, `extractCodexThreadMeta` produced `threadId: ''`, and the thread VANISHED from /api/sessions — then the empty meta was cached by mtime, so for a stopped thread it stayed gone until a restart. Measured on the dev box: compressing the 40 real `~/.codex` rollouts at the DEFAULT zstd level, 7 reproduced it (ratios 4.0–6.0, e.g. plain 1,115,325 → comp 195,087). Fix: `zstdDecompressHead` BISECTS over compressed prefix sizes under a fixed output cap (a truncated prefix decompresses to the plain text it covers — verified on this runtime) until ≥ plainBytes of plain text exist; an unreadable head now THROWS a coded error (`EZSTUNSUPPORTED`/`EZSTHEAD`; zero plain bytes out of non-empty compressed input is a failure, not emptiness) so the existing `extractFailed` rule refuses to cache it, and `_noteExtractFailure` logs the reason verbatim once per file per 10 min. **Invariants: a bounded reader must be bounded by CONSTRUCTION (bisect/stream), never by a guessed compression ratio; "unreadable" and "empty" are different answers and only the second may be cached; a degrade path that hides a thread must say so in the log.**

**② A CACHE GUARD MEASURED THE WRONG CLOCK.** The codex rollout walk's per-directory listing cache (`codex-session-store._listDirCached`) skipped the readdir when the dir mtime was unchanged AND `now - mtime > 2s` — the coarse-timestamp guard evaluated at LOOKUP time. Settledness is a property of the CAPTURE: a listing taken while the mtime tick was still open can miss a sibling created in the same second, and that sibling never bumps the mtime again, so once the clock passed mtime+2s the stale listing was trusted forever (the poll is 5s — the window is always over by the next lookup) and the second rollout never appeared in the session list. Fix: record `settled` at fill time; an unsettled capture is re-read on the next lookup until it is taken settled (the readdir-per-poll win is untouched for settled captures). **Invariant: a freshness/settle predicate is evaluated and STORED when the data is captured — evaluating it at read time answers a question about the reader, not about the data.**

**③ "PLAIN WINS" WAS A COMMENT, NOT A RULE.** `interpretDiscoveryLines` de-duplicated a thread's `.jsonl` and `.jsonl.zst` twins by keeping the FIRST entry, commented "plain wins — first in mtime order". Both producers sort newest-first (hosts.js `sort -rn`, agentd.js `b.mtimeMs - a.mtimeMs`) and compression happens AFTER the last write, so the compressed twin was always first — and the ssh scanner can only read a compressed head where the host has `zstd(1)`, so the remote card silently lost the cwd/name its plain twin's HC/NC lines carried. Fix: group by thread id, prefer the plain twin's facts EXPLICITLY, MERGE what each twin has (either fills a gap), mtime = the newer of the pair, CO on either twin marks the one thread running. **Invariant: when two files describe one entity, the preference is expressed in the predicate, never inherited from an upstream sort; a dedup that drops facts must merge them instead.**
